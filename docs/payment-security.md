# Arunia payment and authorization review

Reviewed 2026-09-17 against current official Toss documentation. This is an implementation/test plan, not a claim that code has passed these checks.

## Verified Toss protocol

- V2 is the browser SDK version; REST payment endpoints remain `/v1/*`. For a new checkout, current docs recommend `TossPayments(clientKey).widgets({ customerKey })`, then `setAmount({ value, currency: 'KRW' })`, `renderPaymentMethods`, `renderAgreement`, and `requestPayment`. `payment().requestPayment` remains a legacy integration. [Current integration routing](https://docs.tosspayments.com/guides/v2/get-started/llms-quick-reference)
- Authentication redirect is not payment success. Persist an order before opening checkout, then compare redirect `orderId` and `amount` with the server record before approval. Pass the stored price to Toss; never derive price from the client. [Payment flow](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)
- Confirm: `POST /v1/payments/confirm` with `{ paymentKey, orderId, amount }`; authenticated payments expire if not confirmed within 10 minutes. Query by `GET /v1/payments/{paymentKey}` or `/v1/payments/orders/{orderId}`. Check response identity, amount, currency, and status. `DONE` permits fulfillment; `WAITING_FOR_DEPOSIT` does not. Preserve `paymentKey`. `totalAmount` remains the original amount after refunds; `balanceAmount` is the remaining refundable amount. [Core API](https://docs.tosspayments.com/reference)
- Authenticate server requests with `Basic base64(secretKey + ':')`. Every POST supports `Idempotency-Key`; use a persisted random UUID per logical operation and reuse it for retries. Keys last 15 days and are scoped to API key, URL, and method. `409 IDEMPOTENT_REQUEST_PROCESSING` means wait/retry. Changing the key after an ambiguous error is unsafe. [Headers and idempotency](https://docs.tosspayments.com/reference/using-api/authorization)
- Toss recommends a 60-second payment API read timeout. A timeout is an unknown outcome, not proof of failure: query/reconcile before offering a replacement payment. Ensure hosting execution limits permit this, or persist recovery work before returning a pending result. [Timeout guidance](https://docs.tosspayments.com/resources/glossary/timeout)
- General payment webhooks have no signature header; `tosspayments-webhook-signature` applies to payout/seller events. Re-query payment state using server credentials before applying a general webhook. Virtual-account deposit events have a `secret` comparison flow. Domestic cancellation completion does not emit `CANCEL_STATUS_CHANGED` (that event serves asynchronous overseas methods). [Webhook events](https://docs.tosspayments.com/reference/using-api/webhook-events)
- Webhooks must receive HTTP 200 within 10 seconds; failed delivery is retried up to seven times. Persist a durable event/work item before acknowledgment and deduplicate processing. An in-memory/background promise on a serverless instance is insufficient. [Webhook delivery](https://docs.tosspayments.com/guides/v2/webhook)
- Cancel: `POST /v1/payments/{paymentKey}/cancel` with required `cancelReason`; omitting `cancelAmount` requests full cancellation. Partial cancellation needs an explicit amount. Persist a separate idempotency key for each refund operation and the returned cancellation `transactionKey`. Paid virtual-account refunds require refund account details; do not advertise instant customer receipt of a refund. [Cancellation guide](https://docs.tosspayments.com/guides/v2/cancel-payment)

## Required application invariants (design recommendations)

1. Bind every order to authenticated `user_id`, request, immutable offer version, amount, and currency. Generate random order IDs server-side. Clients choose an offer ID, never a price, counselor override, role, or payment status.
2. Atomically reserve one payable order for the request/accepted offer. An idempotent confirm protects one order; it does not prevent two different orders from charging the same service. Use database uniqueness/conditional writes, not a Node process mutex.
3. Suggested payment states: `pending -> confirming -> paid`; ambiguous transport/storage errors retain `confirming` or become `reconciliation_required`. Only authoritative provider failure can become failed. `paid -> refund_pending -> refunded` requires a confirmed provider cancellation. Keep service status separate.
4. Before external approval, atomically claim the order and bind its paymentKey. Reject another key, revoked/expired offer, inactive counselor, or incompatible request state. Freeze offer replacement/cancellation while confirmation is unresolved; handle a concurrent administrative change by reconciliation and, if necessary, a separately recorded refund. Do not hold a database transaction open during an HTTP call.
5. A replay of an already-paid order returns its recorded result only after ownership/identity checks. A timeout retry uses the same operation, paymentKey, amount, and idempotency key. On a crash after Toss success but before database commit, reconciliation must recover the paid record and issue service access exactly once.
6. Query on uncertain confirmations, cancellations, and webhook hints. Match provider `orderId`, `paymentKey`, `totalAmount`, currency, and allowed status. Never authorize a transition using only a webhook body or success URL. Persist a durable reconciliation marker and provide a protected retry path; browser refresh alone is not recovery coverage.
7. In Vercel production require remote database configuration; fail closed instead of falling back to local SQLite. Local files/process state cannot enforce sessions, payment uniqueness, rate limits, or recovery across instances. Keep secrets out of `VITE_*`, browser responses, bundles, logs, and Git.
8. Require explicit `APP_DEMO=true` for mock checkout and visibly label results as demo. Missing Toss credentials returns unavailable without marking an order paid. Keep demo/live payment providers and stored records distinct; a demo success never acquires live entitlement. Never silently fall back to mock after a live error.
9. Use unpredictable session tokens with only their hashes in the database, expiration/revocation, `HttpOnly`, `Secure` in HTTPS, and `SameSite=Lax`. Rotate on login; revoke on logout. Password hashing should be asynchronous scrypt with random per-password salts, bounded input size, constant-time comparison, and durable login throttling.
10. Apply an exact configured-Origin check to cookie-authenticated unsafe endpoints, including login/register/logout and admin actions. Require JSON where appropriate; reject untrusted/null/missing origins unless a separately authenticated non-browser path is intentionally defined. Do not derive the allowlist from an untrusted Host header or allow all preview domains. GET handlers must not mutate state.
11. Allowlist admin actions/transitions; verify current database role on each action. Signup cannot assign roles. Do not expose arbitrary status patching that can manufacture `paid`, `refunded`, or `completed`. Record actor, old/new states, reason, and timestamp without logging private counseling text or credentials.

## Minimum meaningful automated tests

Use two ordinary accounts A/B, one admin, an isolated database, and an injectable Toss adapter. Count provider calls and inspect durable rows, not just HTTP status. No real charges are needed.

| Test | Scenario and required result |
| --- | --- |
| IDOR | A cannot read B's request, offers, counseling details, order, receipt, or payment result; cannot accept/cancel/pay B's IDs. Return 403/404 with no private fields and zero provider calls. Cover collection endpoints too. |
| Session boundaries | Expired/revoked/random token gets 401; logout invalidates reuse; login rotates the session. Signup with `role: 'admin'` remains ordinary. Password hashes/session hashes never appear in API responses. |
| CSRF/origin | With a valid cookie, wrong/missing/null Origin and form content types cannot mutate any protected resource, including login/logout. Exact allowed origin succeeds. Reject suffix tricks such as `trusted.example.evil.test`. |
| Price tampering | Send lower, negative, fractional, string, overflowing, or extra `amount` values and modified counselor/offer IDs. No rejected request reaches Toss. Valid approval always sends the stored integer KRW price. |
| Concurrent confirmation | Fire 20 confirmations for the same order/key; observe one logical provider approval and one paid transition. Replays return the same result. A different paymentKey for that order is rejected. |
| Duplicate checkout | Race two create-order calls for one accepted offer/request. Only one payable order exists; two distinct order IDs cannot both enter approval for the same service. |
| Unknown outcome | Stub Toss as successful but throw a timeout before response; then let query return `DONE`. Recovery marks the order paid once using the original identity; no second/new order becomes payable. Repeat with database-write failure after approval. |
| Provider mismatch | Return another orderId/paymentKey, wrong totalAmount/currency, or `WAITING_FOR_DEPOSIT`. No paid entitlement is created; mismatches are retained for investigation. |
| Stale offer | Replace/revoke/expire the offer after checkout creation. Confirm rejects before charging. Race admin replacement against confirm; only the permitted atomic winner proceeds and no paid record references a silently changed price/offer. |
| Admin transitions | Ordinary user cannot call every admin endpoint. Admin cannot jump unpaid -> completed, force paid, cancel a completed/refunded record incorrectly, or mutate an offer during unresolved approval. Valid actions produce audit records. |
| Cancellation retry | Simulate successful cancel followed by timeout; replay/query recovers one refund. Partial cancel retries do not subtract twice. No refund status is set on provider failure. Over-refund or another user's order is blocked before provider calls. |
| Webhook replay/spoof | Forged `DONE`, duplicate events, and out-of-order events cannot grant service or resurrect refunded orders. Only verified current provider state applies, once. Durable failure remains retryable. |
| Deployment gates | Missing production DB or payment credentials fails closed. `APP_DEMO` absent/false disables mock. Mock has zero external payment calls. Built frontend contains neither secret key nor database auth token. |

## Before live activation

Run these tests with the fake adapter now. Once merchant test credentials arrive, run one Toss sandbox checkout plus cancellation and a recovery query using the same production routes. Real payment readiness additionally requires configured live merchant credentials, durable production storage, permitted payment methods, and deployed callback/webhook origins. Do not label unexecuted sandbox/live validation as passed.
